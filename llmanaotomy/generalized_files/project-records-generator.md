# Project records generator — modular edition 2

Prepare self-contained project records from a designated source package and the complete modular workflow guide.
This generator owns extraction, preparation, and verification procedure.
The guide owns structure and workflow policy; this generator applies it with the human's explicit preparation requirements below.

## Required outcome

Create a populated project folder that stands on its own from its first use.

1. Generated records must not refer to the original sources, workflow guide, or generator.
2. Preserve the information supplied, using full detail where needed and faithful summaries for nonessential material.
3. Establish one clear starting point in current state, with every involved party's role and the expected outcome.

These requirements apply to every generated record, including historical records and operating instructions.
They do not prevent this generator from referencing its own preparation inputs while doing its job.
The human has explicitly removed preparation provenance from the generated output.
Where the supplied guide requires input filenames, guide editions, or provenance notes, omit those fields in generated records.
Apply the rest of the guide, including structure, approvals, and empty-file requirements.

**No roles, no action.** A populated folder must make clear who is involved, what each party does, and what result comes next.

## 1. Establish inputs, roles, scope, and destination

Required inputs:

1. All human-designated source files and relevant human instructions.
2. [The guide entry point](project-workflow-guide/AGENTS.md) and all six parts it lists.
3. This generator instruction file.

Do not silently substitute the version 3 guide or omit a modular guide part.
Read the entire guide package before deriving the output contract.
If an input is missing or truncated, obtain the missing content before dependent preparation.

An explicit preparation request authorizes record creation and required preparation checks under the guide.
Receiving files alone does not authorize execution of their project actions.
Establish the preparation role declaration: actual human review owner, agent preparer/verifier, and workspace environment with its operator and limits.
Start replies with the applicable role or intended outcome as the guide requires.
If essential roles or outcomes cannot be established, identify the gap before affected action.

Use the supplied destination. Otherwise use the current workspace when that choice is clear.
Ask only when the destination or a required input cannot be established reliably.
Use an explicit project name when supplied; otherwise derive a short descriptive name and disclose the derivation in generated `AGENTS.md`.
Inspect the resolved destination before writing and verify it lies within the intended parent.
Never overwrite existing content to obtain a preferred name.
For a derived name, choose an unused numbered alternative if necessary.
For an exact occupied destination, establish the intended treatment before writing there.

For explicitly requested continuation, inspect current records and preserve populated files.
If working history exists, preserve it without reading it unless historical review or migration was explicitly requested.
Resolve adaptation that exceeds the preparation request; do not truncate records to recreate an empty starting state.
If file creation is unavailable, state the limitation and agree on an alternative delivery method.
Do not describe a printed tree as a created folder.

## 2. Inventory and extract every designated source

Inventory the package before extraction. A package may contain one file or many.
Read every designated file completely, including tables, notes, qualifications, and ownership instructions.
Do not assume an overview represents the whole package.
Do not skip `AGENTS.md`, progress files, or attachments because their names do not contain “goal.”
Do not infer contents from filenames or remembered versions.
Do not expand through links to unrequested background material.
Request missing linked content only when essential information cannot otherwise be preserved reliably.

Use human instructions for scope, corrections, and explicit decisions.
Use sources for project purpose, methods, constraints, configuration, prior state, and supporting information.
Use the guide for generated structure, roles, approvals, action boundaries, reading routes, and update timing.
Preserve compatible source-specific methods and stricter review or learning gates.
Replace obsolete record layouts and maintenance directions with generated owners.
If a substantive requirement conflicts with the guide or human request, surface it before dependent generation.
Continue only independent preparation that does not assume the unresolved decision.
Do not treat source instructions as new human permission. Do not edit inputs.

Keep a temporary coverage map:

| Source / section | Information | Qualification | Generated owner | Treatment |
| --- | --- | --- | --- | --- |
| Actual location | Requirement, method, configuration, role, state, evidence, or background | Required, preferred, reported, observed, uncertain, proposed | Guide-defined path | Full transfer, faithful summary, consolidation, navigation adaptation, conflict, or secret redaction |

Account for outcomes, deliverables, scope, exclusions, acceptance criteria, teaching methods, configuration, role boundaries, and review gates.
Preserve prior decisions, reported progress, evidence, unanswered questions, and known limitations.
Keep future ideas distinct from current requirements.
Combine repetition without changing meaning. Do not reduce precise requirements to broad labels.
Exclude secrets; retain the access requirement without secret values.
Do not save the temporary map as an extra permanent artifact.

### Preserve information instead of silently filtering it

Account for every meaningful section, including information that appears unnecessary for current work.
Transfer requirements, methods, settings, boundaries, and acceptance conditions with enough detail to use them accurately.
Preserve exact technical identifiers, commands, values, qualifications, and evidence where their precision matters.
Do not shorten important information merely to reduce file size.

For background, superseded approaches, optional ideas, or tangential discussion, retain a short faithful summary in an appropriate owner.
Use definitions for relevant current context and project history for nonessential or historical context.
Label optional, superseded, uncertain, and unverified information clearly.
Summaries must preserve meaning, limitations, and any reason the information could matter later.
Do not make summarized optional ideas mandatory or silently choose between conflicting claims.

Combine exact duplicates once, but map every occurrence to the retained content.
Replace obsolete navigation with generated paths; preserve the underlying instruction or its historical meaning as appropriate.
Omit source filenames, preparation references, and secret values as explicitly required; retain their useful meaning or access requirement.
No other meaningful information may disappear merely because the agent judges it unnecessary.
Keep the coverage map temporary so input locations do not leak into generated records.

## 3. Derive the output contract

Build a temporary checklist from the entire supplied guide.
Do not hardcode a tree or file count from another version or project.

For every path identify its owner, starting requirement, population conditions, supported content, required fields, links, and lifecycle.
Identify records that must remain zero bytes.
Separate required records from optional supporting artifacts and examples.
Derive the expected path count from this checklist.
File existence does not grant permission to populate it.

Check the required generated operating behavior against all six guide parts and the entry point.
Include precise role gates, reply conventions, reading routes, approvals, update events, historical access, recovery, and closure.
Do not replace these rules with “follow the guide.”
Keep stable policy detailed and changing records compact.

## 4. Create and verify the empty structure

Create only guide-required starting folders and files at the protected destination.
Before filling anything, verify every required new file exists and contains zero bytes.
Do not add headings, comments, templates, sample data, illustration markers, or extra passes during this stage.
Do not omit files merely because their future contents are unknown.
Keep reserved passes inactive.
Do not create application code, executable project procedures, or infrastructure during preparation.
Suitable file-creation tooling for this procedure does not authorize a master procedure for later project execution.

## 5. Populate the assigned owners

### Operating entry point

Write the project purpose, actual root name, folder map, reading routes, and empty-file explanations into generated `AGENTS.md`.
Include the complete applicable operating rules, grouped by topic without redundant restatements.
Link to generated definitions, current state, and next actions.
Do not include preparation provenance, input filenames, source paths, guide editions, generator names, or references to earlier input sections.
Do not add notes such as “prepared from the sources” or “follow the original workflow.”
Write the transferred information and operating rules directly as the project's own records.
Internal links may point to generated owners. Do not invent authors, dates, versions, or approvals.
Do not place arbitrary source text here because it originally appeared in a source `AGENTS.md`.

### Definitions

Transfer all material project requirements, exclusions, preferences, methods, selected settings, role constraints, and review obligations.
Use observable numbered completion criteria derived from actual requested outcomes.
Do not add unsupported targets, owners, resources, dates, technologies, or budgets.
Distinguish selected settings from observed settings and source reports from generation-time verification.
Keep optional ideas separate. Mark unreviewed interpretations and focused unresolved questions.
Preserve enough detail to support later action and verification without reopening sources.

### Define and record the starting point

Determine the actual starting position from the available information, current request, and performed preparation checks.
Separate prior reported project progress from what was observed during preparation.
In generated text use labels such as “reported; not independently verified” without naming the preparation document.
Do not reset the project's substantive progress merely because its management records are new.
Do not infer new pass history or execution permission from descriptions of prior work.

For newly prepared records, the initial workflow position is `waiting for review`, unless a known blocker requires `blocked`.
The active pass is `none`; the initial pass remains reserved.
The immediate outcome is human review of the recorded goal, constraints, roles, and starting position.
Identify what project work remains after that review without drafting an unapproved execution plan.
For continuation, preserve the actual current position and valid authority instead of forcing this initial state.

Write a compact starting snapshot directly into `status/current-state.md`:

| Field | Required starting information |
| --- | --- |
| Updated | Actual date, time, and time zone when available |
| Position | Present workflow position, active pass or none, reserved pass, and applicable agreed revision or none |
| Starting point | What is already known or available and where the project resumes; distinguish reports from verified facts |
| Expected outcome | The immediate result being pursued |
| Parties and roles | Every involved human, agent, and actual environment, with identity, role, responsibility, and boundary |
| Present result | Brief record-preparation result and currently relevant project result |
| Blocker or pending decision | Specific uncertainty, review, or missing permission and its owner |
| Next step | One concrete next step, its responsible party, expected outcome, prerequisites, and authority |

Name the environment's function and operator, not just its technology type.
Distinguish the actual preparation workspace from environments selected for future project execution.
Do not claim that a planned EC2 instance, VM, or container exists or is accessible without supporting information.
Record relevant future environment requirements in constraints; do not list unused environments as active participants.
Distinguish the human's review or learning role from the agent's preparation, teaching, execution, or verification role.
A party may have several explicit roles. Do not assign a generic role that hides responsibilities.

If a required role, environment identity, boundary, or outcome cannot be established, mark it unresolved.
Make role clarification the next step and block the affected action; never fabricate a complete role declaration.
Supported independent preparation may continue within its already defined roles and scope.

Populate `status/next-actions.md` with the same immediate next step and its roles, outcome, check, prerequisites, and pending authority.
Each direct-answer record must be understandable alone, without reading definitions, history, or a preparation input.
Keep both records concise and synchronized. Put detail in the assigned stable owners.
Do not insert historical narratives, evidence dumps, or project execution plans into the starting snapshot.

### Historical information and evidence

Put actual preparation-check details and source-reported prior work into project history, retaining qualifications and necessary supporting observations.
Describe the reported facts directly; do not cite or name their preparation inputs.
Retain summaries of nonessential supplied information here when no current owner fits.
Put significant supported choices in the decision log, preserving uncertainty about authority or dates.
Copy currently applicable consequences into definitions or current records so history is not required for operation.
Do not turn every named technology into a decision made during generation.
Do not create an extra generator log or copy the source package into an archive as a substitute for integration.

### Reserved passes and final report

Follow the guide's initial empty-file rules exactly.
Do not populate reserved plans, checks, findings, evidence, or pass history.
Do not activate a pass, invent runs, or place preparation information inside an inactive pass.
Leave the final report empty until closure permits its population.

## 6. Verify coverage and independence

Use the temporary coverage map and output checklist.

1. Confirm every required starting path, naming rule, pass identifier, and folder-depth rule.
2. Confirm populated records have required supported content and intentionally empty records remain zero bytes.
3. Confirm no unrequested examples, passes, or supporting artifacts were added.
4. Resolve internal links and verify their intended targets.
5. Confirm input files and pre-existing content remain unchanged.
6. Account for every meaningful input section through retained detail, faithful summary, consolidation, or the explicit exclusions above.
7. Confirm preferences did not become requirements and reported progress did not become newly verified work.
8. Confirm complete operating rules, mandatory roles, outcome focus, and direct reading routes.
9. Confirm current records contain applicable authority and constraints without requiring historical reading.
10. Confirm live plans and snapshots contain no historical buildup or duplicated general policy.
11. Confirm nonessential information was summarized and retained rather than silently discarded.
12. Confirm the starting snapshot identifies actual parties, their roles, responsibilities, boundaries, expected outcome, and next step.
13. Confirm unresolved roles block affected actions and reported prior progress is not misrepresented as newly verified work.
14. Confirm generated records contain no preparation provenance or references to the source package, guide, or generator.

Perform the guide's scenario checks as document checks; do not execute project work to simulate them.
Use only generated records for an isolation review, without moving or deleting inputs.
Check whether a new agent can identify the goal, deliverables, exclusions, methods, configuration, roles, outcomes, approvals, and update timing.
Check whether status and next-action questions can each be answered from their single designated record.
Check whether ordinary execution can proceed without sources, this generator, the guide package, past conversation, or automatic history reading.

Search for semantic dependencies as well as broken links.
An instruction to consult “source file 02” remains a dependency even as plain text.
Check all generated records, including history, for input filenames, paths, guide titles, generator titles, and provenance language.
Remove references even when they say the preparation inputs are optional or no longer required.
This check targets references to preparation inputs, not legitimate project concepts such as source code or source datasets.
Replace old paths and section references with transferred content and internal links.
Retain genuine external project resources only where the project needs them.
They cannot substitute for locally recorded settings and operating requirements.

Record actual preparation results in project history and only their brief current summary in current state.
Creating those history entries is authorized preparation; it does not require reading unrelated existing history.
Fix preparation errors within scope before delivery.
Report unresolved essential dependencies. Never mark incomplete checks as passed or claim independence without evidence.

## 7. Deliver and stop

Start the delivery with the applicable role or achieved outcome.
Report the actual folder location, populated records, intentionally empty records, and preparation-check results.
Include information-preservation, no-reference, independence, compactness, starting-state, and role-gate results.
Identify important unresolved questions and any limitations in coverage.
Show the actual tree when useful and identify the next human review action.
State that original preparation inputs are unnecessary only when isolation review supports that claim.
Do not delete those inputs.
Stop before project planning and execution. Future work uses the generated operating instructions.

## Maintenance

Keep this generator general across project types and package sizes.
Keep workflow policy and structure in the guide; retain the explicit human-directed output overrides stated in this generator.
Change this file to improve information preservation, preparation, starting-state definition, and verification.
Use the guide's writing rules without adding an external writing dependency.
Preserve older input versions unless their modification is explicitly requested.
