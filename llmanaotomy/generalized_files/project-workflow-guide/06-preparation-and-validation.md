# Preparation and validation

## Preparation scope

An explicit preparation request authorizes record creation and its structural and content checks.
It does not authorize project investigation, implementation, infrastructure creation, publication, or project execution.
Establish preparation roles and outcome before starting: human review owner, agent preparer/verifier, and actual workspace function.
These roles authorize no additional project actions and do not activate a pass.

Read all seven guide files and all designated project sources, including instruction, status, and attachment content.
Extract material requirements, exclusions, methods, configuration, prior decisions, evidence, and uncertainty.
Preserve compatible project-specific methods and stricter review or learning boundaries.
Use the guide for structure and process and the sources for project content.
Replace old navigation and routine maintenance instructions with the generated owners and update rules.
Surface substantive conflicts before affected preparation; do not silently discard a requirement.

## Creation and initial content

1. Resolve the output destination without overwriting existing user content.
2. Map information to the required owners in [Record structure](03-record-structure.md).
3. Create every required starting file empty.
4. Verify paths and zero-byte state before populating any file.
5. Fill supported content and complete operating instructions.
6. Check coverage, internal links, empty records, role gates, compactness, and independence.
7. Present the preparation result and stop for human review.

An empty record means zero bytes: no headings, comments, or templates.
Populate `AGENTS.md`, definitions, current state, and next actions.
Populate project history with actual preparation-check details and supported historical source information.
Populate the decision log only when supported significant decisions belong there.
Leave all five reserved pass records and the final report empty.
Do not place preparation checks or source background inside an inactive pass.

For a new project, active pass and last closed pass are `none`; `pass-001` is reserved.
State the initialization facts in the preparation entry; current state need only show relevant present facts.
Use position `waiting for review`.
Current state summarizes preparation results briefly and identifies roles, blockers, and the next human review.
Next actions contains that review, its expected outcome, responsibilities, and pending decision.
Do not draft the first project pass or invent its action items during preparation.
Project planning and execution remain unapproved unless applicable authority was actually given.

Keep source-reported prior work separate from newly verified facts and new pass history.
Do not claim that mentioned resources exist or source-described checks were performed during preparation.
Preserve unknown decision authority or dates without inventing them.
Do not turn every selected technology into a newly made decision.

For existing working records, preserve populated files, approvals, evidence, and pass history.
Do not reset records to force a new-project state.
Resolve adaptation with the human when the requested preparation does not cover its consequences.
Do not read existing historical files unless explicitly included in the requested review or migration.

## Independence

The generated folder must remain usable without the source package, guide package, generator, or previous conversation.
Transfer necessary information into its assigned generated owner.
Replace source references with internal relative links where needed.
Preserve exact technical identifiers, qualifications, exclusions, review gates, and evidence status.
Embed essential observations when an input would otherwise be their only record.

Do not leave instructions to read a preparation file, consult its section, or update its progress file.
A plain-text dependency is still a dependency, even without a link.
Do not achieve independence by dumping source copies into an extra folder.
Integrate the content and avoid competing copies of current rules or state.

Include one short provenance note in generated `AGENTS.md` with source filenames and the guide's declared edition.
Label them historical preparation inputs, unnecessary for future operation.
Do not link back to preparation files or invent authors, paths, dates, versions, or approval history.
Genuine external project resources, such as datasets or model repositories, may remain required references.
Those references cannot replace the configuration or instructions that belong in the generated records.
Preserve access requirements without copying secrets.

Perform isolation review without moving or deleting inputs.
Check whether the generated records alone explain the goal, scope, methods, configuration, roles, approvals, updates, and current next action.
Check direct status and next-action answers using only their respective records.
Report unresolved essential dependencies and do not claim independence when they remain.

## Writing and compactness

Use simple English, active voice, consistent terms, and focused paragraphs.
Use one instruction per sentence and numbered lists for procedures.
Keep instruction sentences within 20 words and descriptive sentences within 25 words where practical.
Preserve exact technical names, commands, qualifications, and uncertainty.
No external language guide is required.

Stable definitions and operating instructions may be detailed enough to cover applicable edge cases.
Current state, next actions, and plans use compact fields and tables from the structure part.
Do not fill them with historical prose, duplicated policy, exhaustive transcripts, or irrelevant empty fields.
Role and outcome declarations must remain explicit even when records are concise.
Do not make current answers depend on opening links to details.

## Required consistency checks

| Scenario | Expected behavior |
| --- | --- |
| Multiple sources supplied | Every designated file is read and material information accounted for. |
| A party has no defined role | Affected action is blocked before execution. |
| Roles or environment change | Scope and authority are reassessed before changed work. |
| A reply is produced | It starts with the applicable role or intended outcome. |
| Current state is requested | The answer comes directly from current state without history or definitions. |
| Next actions are requested | The answer comes directly from next actions with roles, outcomes, and pending authority. |
| Historical review is not requested | Historical files remain unread; current operation remains possible. |
| Draft changes repeatedly | Draft content remains in conversation; current approved records remain intact. |
| Plan approved but execution pending | No project action executes. |
| First action and check approved | Save the plan checkpoint, then perform only that scope. |
| Action succeeds | Update compact snapshots, report the result, and wait for the next execution approval. |
| Several dependent stages exist | Separate actions and checks retain their human review boundaries. |
| Routine discussion has no state change | No record update is needed. |
| Failure or blocker occurs | Save partial effects and the stopping position before recovery. |
| Session ends during unapproved planning | Save pending status without persisting the draft as an agreed plan. |
| Session ends after work | Save accumulated results, approvals, and exact next action. |
| Technical checks pass but human review is pending | Acceptance remains pending. |
| Reserved files exist | Their existence implies no planning, execution, or completion. |
| Original inputs disappear | Generated records still explain the project and complete operating process. |

These are document consistency checks, not authorization to execute project work for testing.
Check real paths, links, required content, zero-byte files, and preservation of pre-existing content.
Correct preparation errors within the authorized scope before delivery.
Never mark incomplete checks as passed.

## Delivery boundary

Report the actual folder, guide edition, populated records, intentionally empty records, checks, unresolved issues, and next human review.
Show the actual tree when useful, deriving it from created files.
Claim independence only when the checks support it.
Do not delete preparation inputs.
Stop after preparation and verification. Later work follows the generated operating instructions.
