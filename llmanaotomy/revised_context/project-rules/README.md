# Project rules

This folder contains the stable contract: purpose, scope, responsibilities, working agreements, success criteria, and selected technical choices.

Read [project-guide.md](project-guide.md) first.
Then read the document relevant to the work:

| Document | Owns |
| --- | --- |
| [project-guide.md](project-guide.md) | Goal, phase boundaries, exclusions, and completion criteria |
| [learning-method.md](learning-method.md) | Teacher responsibilities, onion-peeling, and learner confirmation |
| [implementation-rules.md](implementation-rules.md) | Code discipline, inspection displays, verification, and investigation records |
| [technical-reference.md](technical-reference.md) | Selected environment, model, dependencies, and technical decision changes |
| [hld.md](hld.md) | High-level design: agreed components, responsibilities, boundaries, and overall flow |
| [lld.md](lld.md) | Low-level design: agreed interfaces and implementation contract for the current operation |

For design work, read HLD before LLD.
Keep design progress in [HLD status](../project-status/hld.md) and [LLD status](../project-status/lld.md).
Keep supporting observations in [HLD evidence](../project-evidence/hld.md) and [LLD evidence](../project-evidence/lld.md).
Update design rules when an agreed decision changes them.

Keep active tasks and observed environment status in [project-status](../project-status/README.md).
Keep experiment results and supporting observations in [project-evidence](../project-evidence/README.md).

Update rules when an agreement or governing decision changes.
Do not change a rule through a progress note alone.
Return to [AGENTS.md](../AGENTS.md) for reading and maintenance routes.
