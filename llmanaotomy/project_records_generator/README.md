# Software and AI project records generator — version 3

Use this Markdown procedure to prepare self-contained software and AI project records from all supplied project files.
It specializes the generalized version 3 generator and uses the software and AI version 3 core workflow.
It is assistant guidance, not an executable application.

## Inputs and use

1. Read the human's request, every designated project source, and the destination requirements.
2. Read the [agent instructions](AGENTS.md) and [generator](software-ai-project-records-generator.md).
3. Read the [core workflow](../software_ai_guides/core/software-ai-development-workflow.md), version 3.
4. Read the [architecture](../software_ai_guides/core/architecture-and-design-guide.md) and [quality](../software_ai_guides/core/engineering-quality-guide.md) guides.
5. Select and read applicable [domain guides](../software_ai_guides/domains/README.md) from actual scope.
6. Map material information to generated owners and derive the required structure from the core.
7. Create and verify empty records before populating supported information and complete operating instructions.
8. Verify structure, coverage, checkpoint behavior, and independence; deliver the result and stop for human review.

An instruction file, status record, attachment, or configuration note may contain essential project information.
Do not use only an overview or goal file when the source package contains more material.
Preparation does not authorize investigation, new designs, pass planning, implementation, experiments, or deployment.

## Dependencies and portability

This reusable generator requires the sibling [guide library](../software_ai_guides/README.md) during preparation.
Keep that sibling layout when relocating these source folders, or update their links.
The guide library remains independently usable and does not require this generator.

Generated projects must operate without the original source package, generator, guide library, or previous conversation.
Transfer necessary requirements, methods, selected configuration, and operating rules into their generated owners.
Use internal relative links and one main owner for each fact.
List preparation filenames and declared versions only in a short historical provenance note.
Genuine external project resources may remain dependencies; preparation inputs must not remain operating dependencies.

## Preparation boundaries

Derive paths and content conditions from the actual core workflow; this index does not duplicate its tree.
Keep generated projects outside the reusable source folders and preserve existing destination content.
Keep reserved pass records and the final report at zero bytes until the workflow permits population.
For new projects, keep active pass and last closed pass at `none`, with position `waiting for review`.
Record preparation checks in current state and distinguish reported prior work from newly verified facts.

Later work follows the generated project's instructions:
**Discuss the plan → approve the plan → explain the next action → approve execution → act → check → review.**
Drafts remain in conversation; each action has its own execution approval and separate check.
Records are saved at the defined checkpoints, including before the first approved execution.
